# StockView 后端面试题（含参考答案）

本文基于当前项目后端实现整理，覆盖：
- Next.js Route Handler
- 第三方行情代理与数据解析
- Supabase 数据与权限
- AI 分析流式接口（LangGraph + SSE）
- 安全、稳定性与可观测性

## 1) 为什么把行情请求放到 `/api/*`，而不是前端直连第三方接口？

**参考答案：**
1. 避免浏览器端 CORS 限制，提升请求成功率。
2. 统一处理第三方接口异常、超时和返回格式差异。
3. 便于在服务端做缓存、限流和熔断。
4. 隐藏第三方调用细节，降低前端复杂度。

**深挖追问：**
1. 如果第三方接口频繁波动，如何给前端提供稳定 SLA？

## 2) `stocks/list` 里“内存缓存 + revalidate”分别解决什么问题？

**参考答案：**
1. 内存缓存（进程内）减少同一实例内重复拉取。
2. `next: { revalidate: 3600 }` 利用框架缓存机制降低外部请求。
3. 两者组合可以降低延迟和成本，但多实例下内存缓存不共享，仍可能重复拉取。

**深挖追问：**
1. 如果部署到多实例，如何升级为 Redis 统一缓存？

---

## 3) 为什么 `stocks/price` 要先 `arrayBuffer()` 再 `TextDecoder('GBK')`？

**参考答案：**
1. 第三方行情源返回 GBK 编码，不是标准 UTF-8 JSON。
2. 直接 `response.json()` 会失败或乱码。
3. 正确流程是先读取二进制，再按 GBK 解码成字符串，最后再解析文本格式。

**深挖追问：**
1. 如果运行环境不支持 GBK 解码，如何降级处理？

## 4) `codes` 参数要做哪些校验？为什么？

**参考答案：**
1. 校验必填与长度上限，避免超长请求拖垮后端。
2. 校验股票代码格式（数字位数、市场前缀规则）。
3. 限制批量条数，避免一次请求拉取过多目标。
4. 结合限流防止恶意刷接口。

**深挖追问：**
1. 你会把限流放在应用层还是网关层？为什么？

## 5) `kline` 接口通过正则提取 `kline_day=...` 的风险有哪些？

**参考答案：**
1. 第三方返回格式一旦变化，正则可能失效。
2. 字段缺失会导致 `JSON.parse` 或映射阶段异常。
3. 应对策略：严格判空、异常捕获、日志告警、返回可识别错误码。

**深挖追问：**
1. 如何实现“格式变更自动告警”而不是等用户反馈？

## 6) 为什么 `analysis` 接口使用流式返回（SSE）？

**参考答案：**
1. AI 分析耗时长，流式输出可显著改善等待体验。
2. 前端可边收边展示 token，降低“卡死感”。
3. 可以按节点反馈进度（fetch/analyze/recommend），便于排障和可观测。

**深挖追问：**
1. SSE 和 WebSocket 在这个场景如何取舍？

## 7) LangGraph 分三段节点（fetch -> analyze -> recommend）的价值是什么？

**参考答案：**
1. 职责清晰：数据整理、分析、建议解耦。
2. 节点边界明确，方便独立调试和重试。
3. 便于插入额外节点（风控、打分、解释性摘要）而不破坏整体流程。

**深挖追问：**
1. 如果 `analyze` 失败，如何设计只重试该节点？

## 8) 这个流式接口该如何做幂等和重试？

**参考答案：**
1. 为每次分析请求分配 `request_id`。
2. 结果按 `request_id + node` 记录状态，避免重复写入。
3. 客户端断线重连时可基于 `request_id` 续拉结果或触发安全重试。

**深挖追问：**

## 9) `supabase anon key` 放前端为什么通常可接受？

**参考答案：**
1. `anon key` 是公开访问入口，不是管理员密钥。
2. 真正安全边界是 Auth JWT + RLS（行级权限）。
3. 如果 RLS 配置错误，即使不泄露密钥也会越权。

**深挖追问：**
1. `service_role key` 为什么绝不能放前端？

2. 网络重试、重复点击都会绕过前端逻辑。
3. 数据库唯一约束才是最终一致性兜底（幂等核心）。

## 13) 第三方行情接口失败时，什么时候“返回旧数据”更合理？

2. 对“交易决策关键链路”，优先一致性，应明确失败而不是悄悄兜底。
3. 需要给前端可识别状态（fresh/stale/error）。

3. API 入参校验 + 限流，防止滥用和资源消耗攻击。
4. 日志脱敏，避免输出用户敏感信息。

## 深挖追问详细参考答案

### 1) 第三方波动时如何给前端稳定 SLA？
1. 先定义 SLA：比如成功率 >= 99%、P95 延迟 < 800ms、陈旧数据窗口 <= 5 分钟。
2. 架构上做三层兜底：本地缓存/Redis 缓存、主备数据源切换、失败降级（stale 数据 + 明确标记）。
3. 接口语义明确化：返回 `data_freshness=fresh|stale`，前端可展示“数据更新时间”。
4. 做熔断与限流：上游连续失败时短路，避免把故障放大到全站。

### 2) 多实例如何升级 Redis 统一缓存？
1. 缓存 key 统一规范：`stocks:list:v1:page={n}:size={m}:search={q}`。
2. 读路径：先查 Redis，miss 再拉上游并回填缓存。
3. 写路径：用“互斥锁 + 双重检查”防缓存击穿（如 Redlock）。
4. 失效策略：TTL + 主动失效（行情更新任务触发）。
5. 监控命中率、回源率和平均回源耗时，持续调 TTL。

### 3) 运行环境不支持 GBK 怎么降级？
1. 优先切换到支持 UTF-8 JSON 的备用行情源。
2. 若必须走该源：把 GBK 解码放到独立 Node 服务处理，前端服务只消费标准 JSON。
3. 在当前接口里检测解码失败并返回 502 + 错误码，不要静默返回空对象。
4. 记录样本 payload（截断）到日志，便于快速确认编码问题。

### 4) 限流放应用层还是网关层？
1. 最佳实践是双层：网关做全局防护，应用层做业务细粒度限制。
2. 网关层优点：低成本挡恶意流量、保护后端资源。
3. 应用层优点：可按用户/接口语义控制（如分析接口单用户每分钟 5 次）。
4. 面试答法：先网关兜底，再在高成本接口加应用层限流。

### 5) 如何实现格式变更自动告警？
1. 建“解析成功率”指标：`parse_success_count / total_count`。
2. 当 5 分钟内成功率低于阈值（如 <95%）触发告警。
3. 日志保留响应样本（前 200 字符）和请求参数，方便回放。
4. 做定时合约巡检任务，主动调用上游校验字段结构。

### 6) SSE 和 WebSocket 如何取舍？
1. 仅服务端单向推送进度/文本时优先 SSE：实现简单、HTTP 友好、运维成本低。
2. 需要双向交互（客户端主动中断、实时控制参数）再考虑 WebSocket。
3. 当前 AI 分析流式输出场景以“单向输出”为主，SSE 更合适。
4. 结论：先 SSE，出现双向强需求再升级 WS。

### 7) `analyze` 失败时如何只重试该节点？
1. 给每个节点独立状态：`pending/running/success/failed`。
2. `fetch` 输出持久化（缓存或数据库），避免重跑前置步骤。
3. 重试策略只针对 `analyze`：指数退避 + 最大重试次数。
4. 若仍失败，返回部分结果（含 fetch 数据）并提示“分析阶段失败”。

### 8) 如何处理重复点击导致并发分析？
1. 客户端：按钮防抖 + in-flight 状态禁用。
2. 服务端：同一 `user_id + ticker + time_window` 生成幂等键。
3. 若已有运行中任务，直接返回已有 `request_id`，避免重复算。
4. 对高成本任务设置并发上限，超限返回可重试提示。

### 9) `service_role key` 为什么不能放前端？
1. 它绕过 RLS，相当于数据库管理员权限。
2. 一旦泄露，攻击者可跨用户读取/修改全量数据。
3. 前端代码和网络请求天然可被查看，无法保密该密钥。
4. 正确做法：只在可信服务端环境使用，并配最小权限。

### 10) 交易业务唯一键如何设计？
1. 常见键：`user_id + stock_code + direction + price + quantity + trade_time + broker`。
2. 如果交易单号存在，优先用 `user_id + broker_trade_id`。
3. 需考虑浮点精度：价格建议转最小货币单位存储（分/厘）。
4. 配合 `ON CONFLICT DO NOTHING/UPDATE` 实现幂等写入。

### 11) 如何验证索引生效？
1. 对慢 SQL 跑 `EXPLAIN (ANALYZE, BUFFERS)` 看是否走目标索引。
2. 关注执行计划中的 `Index Scan`、行扫描数量、耗时。
3. 打开慢查询日志，观察优化前后 P95/P99 改善幅度。
4. 若未命中，检查 where 条件顺序与索引前缀是否匹配。

### 12) 校验放路由层还是服务层？
1. 路由层负责“输入合法性”（类型、必填、格式）。
2. 服务层负责“业务合法性”（权限、状态机、领域规则）。
3. 两层都要有：路由层挡脏数据，服务层保业务一致性。
4. 不建议只放一层，否则要么重复，要么漏校验。

### 13) stale 数据窗口如何定义？
1. 先按业务分级：展示页容忍更高，交易决策页容忍更低。
2. 参考交易时段设阈值：盘中 30-60 秒，非盘中可放宽到数分钟。
3. 把阈值配置化，支持按接口动态调整。
4. 返回响应里附带 `as_of` 时间戳，前端明确展示陈旧程度。

### 14) 最小可行安全审计怎么做？
1. 清单化检查：密钥管理、RLS、鉴权中间件、输入校验、日志脱敏。
2. 做 3 类用例：越权读、越权写、未登录访问敏感接口。
3. 跑依赖漏洞扫描和基础 SAST，修高危项。
4. 形成审计报告：发现项、风险等级、修复责任人和截止日期。

### 15) 日志/指标/追踪先做哪个？
1. 第一优先做结构化日志，因为投入最低、见效最快。
2. 第二步做指标（错误率、延迟、QPS）用于告警。
3. 第三步做链路追踪，用于复杂跨服务排障。
4. 面试可总结为：“先可见，再可量化，最后可追踪”。

### 16) SSE 如何在 CI 稳定测试？
1. 用固定 mock LLM 输出，避免随机文本导致断言波动。
2. 按事件序列断言（节点开始、token 流、节点完成），不要只断全文字。
3. 设置超时和重试，避免 CI 偶发网络抖动导致误报。
4. 增加断线重连测试，验证恢复逻辑和幂等行为。

### 17) 先优化哪条链路，依据是什么？
1. 先看数据：错误率最高、耗时最长、请求量最大的链路优先。
2. 通常先优化“高频 + 高耗时”的行情查询接口，ROI 最高。
3. 对高成本 AI 接口优先做限流与缓存，控制成本波动。
4. 每次优化都设基线指标，确保收益可量化。

### 18) 何时引入中间层的客观信号？
1. 频繁出现前端无法安全处理的密钥/权限需求。
2. 出现跨用户批处理、复杂事务或工作流编排需求。
3. 前端直连导致业务规则分散、重复实现、难审计。
4. 监控上表现为错误定位慢、改动回归风险高、迭代效率下降。
